Application Stage

C'est la première étape du pipeline, entièrement exécutée sur le CPU. C'est toi qui la codes intégralement — contrôle total, optimisations libres.

Ce qui s'y passe
Gestion de la scène, frustum culling, tri des draw calls, input, IA, physique, animation. Tout ce qui tourne avant que les données arrivent au GPU.
Levier principal d'optimisation
Multithreading du recording des command buffers. Et déplacer certains calculs vers des compute shaders GPU (culling, particles, skinning).

Compute shaders

Certaines tâches de l'application stage peuvent être déportées sur le GPU via des compute shaders — programmes GPU qui tournent en dehors du pipeline graphique classique (pas de vertices, pas de rasterisation).

Le GPU est un processeur massivement parallèle. Une RTX 4070 a 5888 CUDA cores capables de traiter des dizaines de milliers d'opérations simultanées. Un i9 a 24 cœurs. Pour le même calcul répété N fois sur des données différentes, le GPU est bien plus rapide.
Cas d'usage compute shader
Frustum culling GPU (10k AABB en parallèle), simulation de particules, post-processing, animation (matrices de skinning), physics broad phase.
Limite du GPU
Un warp = 32 threads exécutent la même instruction. Les branchements complexes (if/else différents par thread) causent la warp divergence — la moitié des cores est idle.
Sortie de l'application stage : une liste de primitives géométriques (triangles, lignes, points) avec leurs données associées, envoyée au geometry stage pour traitement GPU.

Vertex Shading

Le vertex shader tourne sur chaque vertex individuellement. Son rôle principal : calculer la position finale du vertex à l'écran. Il peut aussi calculer des données supplémentaires (normales, UV, couleurs) transmises aux stages suivants.

Les espaces de transformation

Un mesh passe par plusieurs espaces successifs avant d'arriver à l'écran :

Model space → Model transform (MVP) → World space → View transform → View/Eye space → Projection → Clip space → NDC → Screen space
Model space → World space
La model transform positionne et oriente le mesh dans le monde. Plusieurs instances du même mesh peuvent avoir des transforms différentes sans dupliquer la géométrie.
World space → View space
La view transform place la caméra à l'origine, regardant vers -Z, Y vers le haut. Simplifie le clipping et la projection — tout est relatif à la caméra.

Projection

Orthographique
Vue volume = boîte rectangulaire. Les lignes parallèles restent parallèles. Utilisé pour les vues techniques, éditeurs 2D.
Perspective
Vue volume = frustum (pyramide tronquée). Les objets éloignés paraissent plus petits. Correspond à la perception humaine — utilisé dans les jeux.
Après projection, les coordonnées sont en clip coordinates (homogènes, avant division par w). Le GPU sort toujours ces coordonnées du vertex shader pour que le stage de clipping fonctionne correctement.

Stages optionnels

Après le vertex shader, trois stages optionnels peuvent s'enchaîner dans cet ordre. Leur disponibilité dépend du hardware.

1. Tessellation Hull → Tessellator → Domain
Subdivise des patches de vertices en un plus grand nombre de triangles. Permet d'adapter la densité géométrique à la distance caméra — proche = beaucoup de triangles, loin = peu. Typiquement utilisé pour les terrains et les surfaces courbes.
2. Geometry Shader
Prend des primitives en entrée et peut en générer de nouvelles. Moins puissant que la tessellation, mais utile pour la génération de particules — un point en entrée devient un quad face caméra en sortie. Utilisation limitée en pratique moderne (souvent remplacé par les compute shaders).
3. Stream Output
Permet de récupérer les vertices processés dans un buffer GPU sans passer par la rasterisation. Le GPU devient un moteur de géométrie — les données peuvent être réutilisées par le CPU ou en passe GPU suivante. Typiquement pour les simulations de particules.
Ces trois stages sont rarement utilisés en rendu moderne. Le compute shader couvre la plupart de leurs cas d'usage avec plus de flexibilité.

Clipping & Screen Mapping

Clipping

Seules les primitives dans le view volume doivent être rendues. Le clipping élimine ou coupe les primitives qui débordent.

Entièrement dans le frustum
Transmise telle quelle au stage suivant.
Entièrement hors du frustum
Éliminée, ne va pas plus loin dans le pipeline.
Partiellement dans le frustum
Clippée contre le view volume. Les vertices hors volume sont remplacés par de nouveaux vertices aux intersections. La projection en amont fait que le clipping se fait toujours contre le même unit cube — ce qui simplifie et uniformise le calcul.
Après clipping, une division perspective est effectuée (division par w) pour passer en NDC (Normalized Device Coordinates) — un cube de (-1,-1,-1) à (1,1,1).

Screen Mapping

Les coordonnées NDC sont transformées en coordonnées écran (pixels). X et Y sont mappés sur la fenêtre, Z est mappé sur [0,1] pour le depth buffer. À noter : OpenGL place l'origine (0,0) en bas à gauche, DirectX en haut à gauche — une source fréquente de confusion lors de transitions entre APIs.

En Vulkan : Y est inversé par rapport à OpenGL. (0,0) est en haut à gauche. À prendre en compte dans la projection matrix ou avec VK_KHR_maintenance1 qui permet d'inverser le viewport.

Rasterization

La rasterisation convertit les triangles 2D (en screen space) en fragments — les pixels potentiels qui couvrent la surface du triangle. C'est la jonction entre le geometry processing et le pixel processing.

Triangle Setup

Calcule les différentielles, les équations d'arêtes et autres données nécessaires pour l'étape suivante. Effectué par hardware fixe — pas programmable.

Triangle Traversal

Pour chaque pixel dont le centre est couvert par le triangle, un fragment est généré. Les attributs du fragment (profondeur, UV, normales, couleurs) sont interpolés depuis les trois vertices du triangle.

Point sampling
Un point au centre du pixel. Si le centre est dans le triangle → pixel couvert. Simple, mais aliasing visible sur les bords.
MSAA
Plusieurs samples par pixel. Améliore la qualité des bords. La couverture est calculée par sample, mais le shading peut être mutualisé.
Interpolation perspective-correct : les attributs ne s'interpolent pas linéairement en screen space avec la projection perspective. La rasterisation applique une correction pour que l'interpolation soit correcte en 3D — sinon les textures se déforment sur les triangles obliques.
Les fragments générés ici sont ensuite envoyés au pixel/fragment shader pour calculer la couleur finale, puis au merging stage (depth test, stencil, blending) avant d'atterrir dans le framebuffer.
