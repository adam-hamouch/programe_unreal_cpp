En engine dev : vector est ton défaut absolu. Contiguous en mémoire = cache-friendly = traversal rapide pour systèmes ECS. list est quasi jamais justifié — ses insertions O(1) ne compensent pas le cache thrashing.

Équivalents Unreal Engine UE5

STLUnrealDifférences notables
vector<T> TArray<T> API similaire. Intégré au GC Unreal (UPROPERTY). Reserve(), Add(), RemoveSwap() (O(1) si ordre sans importance).
unordered_map<K,V> TMap<K,V> Hash map mais implémentation différente. Pas directement compatible STL. Supporte UPROPERTY. FindOrAdd(), Find() retourne un pointeur.
unordered_set<K> TSet<K> Hash set. Contains(), Add(), Remove(). Compact, bon pour listes d'entités uniques.
array<T,N> TArray<T> + Reserve Pas d'équivalent direct taille fixe compile-time. Utiliser TArray avec Reserve ou un C-array aligné.
string FString / FName FName = string hashée, comparaison O(1), idéale pour les asset names. FString = string mutable, coûteuse.
Piège fréquent : mélanger TMap et std::unordered_map dans un même module. Préférer les types Unreal dans le code engine UE pour la compatibilité GC et les outils de debug (Insights, Memory profiler).
// TArray : RemoveSwap si ordre sans importance → O(1) vs O(n) TArray<AActor*> activeEnemies; activeEnemies.RemoveSwap(deadEnemy); // swap avec le dernier, pop back // FName pour asset keys : comparaison O(1) via hash TMap<FName, UTexture2D*> textureRegistry; textureRegistry.Add(FName("Rock_Albedo"), albedoTex); auto* tex = textureRegistry.Find(FName("Rock_Albedo")); // ptr ou nullptr // TSet pour entités uniques (ex : entités dans un frustum) TSet<AActor*> visibleActors; visibleActors.Add(actor); if (visibleActors.Contains(actor)) { /* ... */ }

Patterns de performance en engine dev

1 — Flat array + index plutôt que pointeurs
// ✗ Pointer soup : cache miss à chaque déréférencement std::vector<Component*> comps; // ✓ Flat array dense : traversal O(n) cache-friendly std::vector<TransformComponent> transforms; // contigu uint32_t entityIndex = entityToIndex[entityID]; // lookup O(1)
2 — Reserve() avant une boucle d'insertions
// Sans reserve : réallocations multiples, copies O(n) à chaque fois std::vector<DrawCall> drawCalls; drawCalls.reserve(MAX_DRAW_CALLS); // 1 seule alloc for (auto& mesh : visibleMeshes) drawCalls.push_back(buildDrawCall(mesh));
3 — unordered_map avec clé numérique > string
// ✗ Hash de string à chaque lookup : coûteux std::unordered_map<std::string, Pipeline> pipelineCache; // ✓ Hash d'un uint64 (hash du nom précalculé, ou ID numérique) std::unordered_map<uint64_t, Pipeline> pipelineCache; uint64_t key = hashString("PBR_Opaque"); pipelineCache[key] = pipeline;
4 — swap-and-pop pour suppression O(1) dans un vector
// ✗ erase(it) : O(n) à cause du shift entities.erase(std::find(entities.begin(), entities.end(), dead)); // ✓ swap avec le dernier + pop_back : O(1) auto it = std::find(entities.begin(), entities.end(), dead); std::swap(*it, entities.back()); entities.pop_back();

Réflexe Leetcode : si le problème demande "est-ce que X existe" → unordered_set. "Combien de fois X apparaît" → unordered_map. "Le minimum/maximum" → priority_queue. "Dans l'ordre" → map ou tri de vector.
// Two Sum → unordered_map, O(n) total std::unordered_map<int,int> seen; for (int i = 0; i < nums.size(); i++) { int complement = target - nums[i]; if (seen.count(complement)) return {seen[complement], i}; seen[nums[i]] = i; } // Longest substring without repeat → unordered_set, sliding window std::unordered_set<char> window; // Merge k sorted lists → priority_queue (min-heap) std::priority_queue<int, std::vector<int>, std::greater<int>> minHeap;
